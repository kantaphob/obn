# รายงานตรวจ Loan — 20 ตุลาคม 2569

## ข้อสรุป
ยังไม่ควรยืนยันว่าระบบถูกต้องครบทุกกรณี พบจุดที่ต้องแก้ด้านสิทธิ์แยกบริษัท การเปลี่ยนรูปแบบดอกเบี้ย และความสอดคล้องระหว่างสูตรยอดหนี้กับตารางงวด

การตรวจครั้งนี้อ่านโค้ด เส้นทาง API ฐานข้อมูลจริงแบบ read-only และเรียกสูตร/ตัวจัดการแก้รูปแบบดอกเบี้ยด้วยข้อมูลจำลองและฐานข้อมูลจำลอง ไม่เปลี่ยนรายการเงิน สัญญา หรือสิทธิ์จริง

ตรวจผ่านเบราว์เซอร์ได้ถึงหน้าเข้าสู่ระบบเท่านั้น จึงยังยืนยันการส่งแบบฟอร์มครบเส้นทางด้วยบัญชีจริงไม่ได้ ข้อสรุปด้านสิทธิ์อ้างอิงการตรวจโค้ด ไม่ใช่การทดลองโจมตีด้วยบัญชีจริง

## ผลที่ตรวจได้
- สัญญา 22 รายการ: ปิด 11, ใช้งาน 4, จอง 6, ยกเลิก 1
- ทั้งหมดเป็น LUMP_SUM ยังไม่มีข้อมูลผ่อน INSTALLMENT จริงให้เทียบ
- 15 สัญญาไม่มี companyCode ที่โค้ดใช้แยกบริษัท รวม 3 สัญญาที่ยังใช้งาน
- ไม่พบใบรับที่ยอดรวมต่างจากเงินต้น + ดอกเบี้ย + ค่าปรับ
- ไม่พบวันที่สัญญาเสียหรือ foreign-key violation; SQLite integrity_check = ok
- ยังไม่มีคำขอทุนและรอบบัญชีปิดจริงให้ตรวจประวัติการทำงาน
- การทดสอบจำลอง 12 ข้อ: ผ่าน 7, ไม่ผ่าน 5
- TypeScript ทั้งโปรเจกต์ยังมี 3 ข้อผิดพลาดใน components/admin/CompanySequenceManager.tsx
- ESLint ในขอบเขต Loan พบ 2 ข้อผิดพลาดเดิมที่หน้าพิจารณาอนุมัติและหน้าบันทึกงาน
- Database migrations 51 ชุดตรงกับฐานข้อมูลปัจจุบัน

## จุดที่ควรแก้ก่อนใช้งานต่อ

### P1 — การจำกัดข้อมูลตามบริษัทไม่สม่ำเสมอ
`lib/authorization.ts:20` ตรวจสิทธิ์ระดับเมนู/แอป แต่ไม่ได้ยืนยันสิทธิ์ในบริษัทของแต่ละสัญญาเอง ขณะที่ `app/api/repayments/route.ts:22`, `app/api/contracts/list/route.ts:67`, `app/api/contracts/[id]/disburse/route.ts:89` และ `app/api/contracts/[id]/terms/route.ts:44` อ่านหรือแก้ตามรหัสสัญญาโดยไม่ตรวจ companyCodes แบบหน้าบัญชีใหม่

นอกจากนี้ `lib/loan-dashboard.ts:24` อ่านสัญญาและรายการบัญชีทั้งหมดโดยไม่ใช้ getCurrentAccess กรองสิทธิ์บริษัท/การเงิน

ผล: หากตั้งผู้ใช้ให้ดูเฉพาะบริษัท การมีสิทธิ์เมนูอาจยังเพียงพอให้อ่านหรือแก้สัญญาของบริษัทอื่นได้ และ Dashboard อาจแสดงข้อมูลนอกสิทธิ์ ควรมีตัวตรวจสิทธิ์บริษัทกลาง ใช้ทั้งการอ่านและการเขียน รวมถึงฝั่ง server-rendered Dashboard และทดสอบด้วยผู้ใช้จำกัดสิทธิ์สองบริษัท

### P1 — ข้อมูลเดิมยังไม่ผูกบริษัท
ยืนยันจากข้อมูลจริงว่ามี 15 สัญญาไม่มีรหัสบริษัท ส่วนการปิดรอบใน `app/api/loan-workspace/route.ts:146` เลือกเฉพาะรายการที่มี companyCode ตรงกับบริษัท และหน้าแยกบริษัทกรองใน `lib/loan-operations-data.ts:27`

ผล: ข้อมูลเก่าอาจไม่รวมในยอดแยกบริษัท/รอบบัญชี แม้ยังปรากฏในยอดรวม ควรทำรายงานรายการยังไม่จัดสรร แสดงยอดที่ตกขอบเขต และให้เจ้าของข้อมูลยืนยันการผูกบริษัท/สาขา ไม่เดาจากชื่อหรือใส่บริษัทให้อัตโนมัติ

### P1 — เปลี่ยนรูปแบบดอกเบี้ยอย่างเดียวแล้วไม่คำนวณยอดจ่ายใหม่
`app/api/contracts/[id]/terms/route.ts:47` อัปเดตเฉพาะ interestMode โดยไม่เปลี่ยน netDisbursed และตารางงวด

ทดสอบตัวจัดการ API ด้วยข้อมูลจำลอง: เงินต้น 5,000 บาท ดอกเบี้ย 500 บาท เปลี่ยนจากเก็บตามงวดเป็นหักล่วงหน้า API ตอบ 200 แต่ netDisbursed ยังเป็น 5,000 บาท แทนที่จะเป็น 4,500 บาท เส้นทางจ่ายเงินจริงใช้ netDisbursed จึงมีความเสี่ยงจ่ายเกินและไม่เหลือดอกเบี้ยรอรับ

ควรใช้การคำนวณเงื่อนไขชุดเดียวกันทุกเส้นทาง แล้วเปลี่ยนรูปแบบดอก ยอดจ่าย ตารางงวด และข้อมูลเอกสารในธุรกรรมเดียว ก่อนอนุญาตจ่ายจริง

### P1 — ดอกเบี้ยรายเดือนกับตารางงวดไม่ตรงกันในวันครบงวด
`lib/loan-balance.ts:37` เริ่มนับเดือนที่ offset 0 และนับวันครบรอบตรงวันตรวจด้วย แต่ตารางงวดเริ่มครบกำหนดหลังหนึ่งเดือน

ตัวอย่างจำลอง: เงินต้น 12,000 บาท ดอก 1% ต่อเดือน 12 เดือน เริ่ม 1 ม.ค. งวดแรก 1 ก.พ. ตารางงวดกำหนดดอก 120 บาท แต่ยอดหนี้คิดดอกแล้ว 240 บาท จ่ายตามงวด 1,120 บาทแล้วถูกตัดเงินต้นเพียง 880 บาท ทำให้งวดแรกยังแสดงค้าง 120 บาท

ต้องตกลงว่าคิดดอกต้นรอบหรือปลายรอบ แล้วให้สูตรยอดหนี้ ตารางงวด การตัดรับ และคาดการณ์ใช้กำหนดเดียวกัน ก่อนเปิดใช้แบบผ่อนรายเดือน

### P2 — ปิดก่อนกำหนดแล้วตารางงวดแสดงเงินรับเกินจริง
`lib/loan-operations-calculations.ts:47` ใช้สถานะ CLOSED เพื่อกำหนดต้นและดอกของทุกงวดว่าเป็นเงินที่จ่ายแล้ว

ตัวอย่างจำลอง: รับเงินจริง 12,120 บาทเพื่อปิดก่อนกำหนด แต่ตารางรวม paid = 13,440 บาท เพราะรวมดอกอนาคตที่ไม่ได้เก็บ ควรแยก “รับเงินจริง”, “ยกเว้น/ลดดอก”, “ยกเลิกงวดที่เหลือ” และ “ปิดสัญญา” โดยใช้ข้อมูลเงินรับจริงคำนวณ paid เสมอ

### P2 — การปัดเศษดอกเบี้ยคนละจังหวะ
`app/api/contracts/route.ts:155` ปัดยอดรวมทั้งสัญญา แต่ `lib/loan-balance.ts:36` ปัดรายเดือนก่อนรวม

กรณีเงินต้น 100 บาท ดอก 0.3333% ต่อเดือน 3 เดือน: สัญญาบันทึก 1.00 บาท แต่สูตรยอดหนี้รวม 0.99 บาท ควรคำนวณเป็นสตางค์ด้วยเกณฑ์เดียวและปรับเศษในงวดสุดท้าย ไม่พบความต่างนี้ในข้อมูลจริง 22 สัญญาที่ตรวจ

### P2 — การเปิดอ่านรายการสัญญาเปลี่ยนสถานะข้อมูลด้วย
`app/api/contracts/list/route.ts:19` และส่วนถัดไปมี updateMany แม้ผู้ใช้ได้รับอนุญาตเพียง contracts:read และไม่ได้จำกัดบริษัท

ควรย้ายการเปลี่ยนสถานะไปขั้นตอนเขียนที่มีสิทธิ์และบันทึกประวัติ หรือคำนวณสถานะแสดงผลโดยไม่เขียนฐานข้อมูล การเปิดดูรายการไม่ควรเปลี่ยนสถานะของสัญญาทั่วระบบ

## สิ่งที่ยืนยันในกรณีจำลองว่าผ่าน
- ดอกเบี้ยหักล่วงหน้าไม่ถูกตั้งเป็นดอกเบี้ยรอรับซ้ำ
- ตารางงวดไม่เรียกเก็บดอกที่หักล่วงหน้าอีกครั้ง
- ยกเว้นค่าปรับแล้วยังคงนับวันเกินกำหนด
- ยกเว้นค่าปรับทำให้ค่าปรับเป็นศูนย์
- ใบรับพร้อมรายการกลับบัญชีให้กระแสเงินสดสุทธิศูนย์
- ใบรับพร้อมรายการกลับบัญชีหักเงินต้น/ดอกในรายงานสุทธิกลับเป็นศูนย์
- การตัดเงินต้น ดอกเบี้ย ค่าปรับ รวมเท่ากับจำนวนเงินที่รับ

ผลผ่านเหล่านี้ครอบคลุมเฉพาะกรณีที่จำลอง ไม่ใช่การรับรองทุกเส้นทางธุรกรรมจริง

## ข้อแนะนำเพิ่มเติม
1. จัดการข้อ P1 ก่อนเพิ่มความสามารถใหม่ โดยเริ่มสิทธิ์บริษัทและข้อมูลเดิมที่ยังไม่จัดสรร
2. เพิ่มชุดทดสอบถาวรสำหรับผ่อนรายเดือน รับบางส่วน ปิดก่อนกำหนด ย้อนวันที่ กลับรายการ และปิด/เปิดรอบ
3. ใช้ฐานข้อมูลสำเนาในการทดลองเต็มเส้นทาง ทั้งผู้ใช้เจ้าของและผู้ใช้จำกัดบริษัท
4. หลังแก้ ให้เทียบยอดหนี้/เงินรับ/ทุน/เงินสดระหว่าง Dashboard สมุดบัญชี ตารางงวด และยอดปิดรอบด้วยชุดข้อมูลเดียวกัน
5. เพิ่มการเชื่อมแผนเงินสดกับรายการเงินจริง เพื่อลดการลืมนำแผนออกและคาดการณ์ซ้ำ
6. ลดการโหลดข้อมูลทั้งหมดทุก 10 วินาทีด้วยการแบ่งหน้า/เลือกเฉพาะข้อมูลของหน้าที่เปิด เมื่อปริมาณข้อมูลเพิ่ม

## ขอบเขตที่ยังไม่ได้รับรอง
- การกดบันทึกทุกแบบฟอร์มในเบราว์เซอร์ด้วยบัญชีจริง
- ธุรกรรมพร้อมกันหลายผู้ใช้และการกู้คืนเมื่อเครือข่ายขาดระหว่างบันทึก
- ผลทางบัญชี ภาษี หรือความชอบด้วยกฎหมายของเงื่อนไขดอกเบี้ย/ค่าปรับ

ไม่มีการแก้รายการเงินจริงหรือแก้สูตรในรอบการตรวจนี้

## สถานะหลังแก้ไขตามคำขอ

แก้การกรองบริษัทในเส้นทางอ่าน/เขียนสัญญา รับชำระ จ่ายกู้ ร่าง และ Dashboard รวมถึงการเข้าถึงเอกสารที่เชื่อมกับข้อมูลเหล่านี้แล้ว ย้ายการเปลี่ยนสถานะที่เกิดตอน GET ไปเป็นการคำนวณสถานะแสดงผลโดยไม่แก้ฐานข้อมูล

แก้ netDisbursed และตารางงวดเมื่อเปลี่ยนรูปแบบดอกแบบย่อ แก้การคิดรายเดือนให้ครบกำหนดตามงวดและแบ่งจากยอดดอกทั้งสัญญา แยกเงินรับจริงออกจากยอดงวดที่ยกเว้นเมื่อปิดก่อนกำหนด

เพิ่มหน้าจัดสรรบริษัทสำหรับข้อมูลเดิมในหน้ากระทบยอด พร้อมเหตุผลและบันทึกประวัติ ไม่มีการเดาหรือจัดสรรบริษัทให้ 15 สัญญาเดิมโดยอัตโนมัติ เจ้าของระบบยังต้องตรวจเลือกบริษัท/สาขาจริงก่อนยอดแยกบริษัทและปิดรอบจะครบถ้วน

เพิ่มชุดตรวจซ้ำ `npm run check:loan` จำนวน 26 ข้อ ผ่านครบ แก้ TypeScript 3 จุดในหน้าจัดการบริษัทและ ESLint 2 จุดในหน้า Loan ที่พบระหว่างตรวจด้วย

การยืนยันผ่านเบราว์เซอร์ด้วยบัญชีจริงและธุรกรรมพร้อมกันยังไม่อยู่ในผลตรวจผ่านนี้

ตรวจ TypeScript รอบล่าสุดพบข้อผิดพลาด 2 จุดในส่วน YouTube (ชนิดข้อมูล MemberOption) ซึ่งอยู่นอกการแก้ Loan ครั้งนี้ ส่วน Loan ไม่พบข้อผิดพลาดจากการตรวจครั้งล่าสุด
